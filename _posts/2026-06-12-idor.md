## 들어가며

IDOR(Insecure Direct Object Reference)는 OWASP Top 10에서 꾸준히 상위권을 차지하는 취약점이지만, 자동화 도구로 탐지하기 가장 까다로운 유형 중 하나로 꼽힌다. SQL Injection이나 XSS처럼 페이로드를 주입해 명확한 시그널(에러 메시지, 스크립트 실행 등)을 얻는 방식이 아니라, **권한 모델 자체의 논리적 결함**을 찾아야 하기 때문이다. 이번 글에서는 IDOR의 본질적인 어려움과, 이를 자동화 파이프라인에서 어떻게 탐지할 수 있는지를 다룬다.

## 1. IDOR이 자동화하기 어려운 이유

일반적인 취약점 스캐너는 다음과 같은 방식으로 동작한다.

1. 요청을 보낸다
2. 응답을 받는다
3. 응답에서 특정 패턴(에러, 반사된 페이로드 등)을 찾는다

하지만 IDOR은 "정상적인 응답"이 곧 취약점의 증거다. 예를 들어 다음 요청을 보자.

```http
GET /api/users/1024/profile HTTP/1.1
Authorization: Bearer <user_A_token>
```

이 요청이 `200 OK`와 함께 사용자 1024의 프로필 정보를 반환한다면, 이것이 취약점인지 아닌지는 **"현재 토큰의 소유자가 사용자 1024여야 하는가"**라는 비즈니스 로직을 알아야만 판단할 수 있다. 스캐너는 HTTP 레벨에서 이 컨텍스트를 알 수 없다.

## 2. 차등 응답 분석(Differential Response Analysis)

이를 해결하는 한 가지 접근은, 동일한 엔드포인트에 대해 서로 다른 권한을 가진 두 계정으로 요청을 보내고 응답을 비교하는 것이다.

```python
def test_idor(endpoint: str, object_id: str, token_a: str, token_b: str):
    """
    token_a: 객체의 정당한 소유자
    token_b: 다른 사용자 (소유자가 아님)
    """
    resp_owner = requests.get(
        f"{endpoint}/{object_id}",
        headers={"Authorization": f"Bearer {token_a}"}
    )
    resp_other = requests.get(
        f"{endpoint}/{object_id}",
        headers={"Authorization": f"Bearer {token_b}"}
    )

    if resp_owner.status_code == 200 and resp_other.status_code == 200:
        if similarity(resp_owner.text, resp_other.text) > 0.9:
            return "POTENTIAL_IDOR"
    return "OK"
```

이 방식은 두 응답이 모두 성공(200)이고 내용까지 유사하다면, 권한 검증 로직이 누락되었을 가능성이 높다고 판단한다. 다만 이 접근은 **사전에 두 개 이상의 테스트 계정과 객체 소유권 매핑**이 필요하다는 전제가 있다.

## 3. 객체 ID 패턴 추론

또 다른 접근은 API 명세(OpenAPI/Swagger)나 트래픽 로그에서 객체 식별자(ID, UUID, slug 등)의 패턴을 추출하고, 이를 자동으로 변조해보는 것이다.

```python
import re

def extract_object_ids(url: str) -> list[str]:
    # 숫자 ID, UUID 패턴 탐지
    patterns = [
        r'/(\d+)(?:/|$)',
        r'/([0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12})'
    ]
    matches = []
    for pattern in patterns:
        matches.extend(re.findall(pattern, url))
    return matches
```

탐지된 ID에 대해 인접 값(`+1`, `-1`), 다른 사용자의 알려진 ID, 혹은 무작위 UUID로 치환한 요청을 보내고 응답 코드와 본문 구조를 비교하는 식으로 자동화할 수 있다.

## 4. 정적 분석과의 결합: 권한 검증 코드 누락 탐지

동적 테스트만으로는 모든 엔드포인트를 커버하기 어렵다. 정적 분석(SAST) 단계에서 권한 검증 코드의 존재 여부를 패턴으로 확인하는 것도 유효하다. Semgrep 규칙 예시:

```yaml
rules:
  - id: missing-ownership-check
    languages: [python]
    severity: WARNING
    message: "객체 조회 후 소유권 검증 로직이 없을 수 있습니다"
    patterns:
      - pattern: |
          $OBJ = $MODEL.objects.get(id=$ID)
          ...
          return $RESPONSE
      - pattern-not: |
          $OBJ = $MODEL.objects.get(id=$ID)
          ...
          if $OBJ.user != $REQUEST.user:
              ...
          ...
          return $RESPONSE
```

이런 규칙은 오탐률이 높을 수밖에 없지만, "이 함수는 권한 검증 코드 리뷰가 필요하다"는 우선순위 신호를 제공하는 것만으로도 충분한 가치가 있다.

## 5. 실전 체크리스트

IDOR 점검 시 확인할 항목들을 정리하면 다음과 같다.

- 객체 ID가 순차적(incremental)인가, 혹은 추측 가능한 패턴인가
- 동일 권한 레벨의 다른 사용자 계정으로 동일 요청 시 응답이 동일한가
- GET뿐만 아니라 PUT/PATCH/DELETE 요청에서도 소유권 검증이 이루어지는가
- 응답 본문에 노출되는 필드가 요청자의 권한 수준과 무관하게 동일한가
- 배치 처리(batch API)나 export 기능에서 필터링이 누락되지는 않았는가

## 마무리

IDOR은 "코드가 틀려서"가 아니라 "검증 로직이 존재하지 않아서" 발생하는 취약점이라는 점에서, 자동화 도구의 한계가 명확하게 드러나는 영역이다. 차등 응답 분석, ID 패턴 추론, 정적 분석을 조합하면 탐지 범위를 넓힐 수 있지만, 최종적으로는 비즈니스 로직을 이해하는 분석가의 검토가 반드시 필요하다. 자동화는 "어디를 봐야 하는지"를 좁혀주는 도구로 활용하는 것이 현실적인 접근이다.
